formatter

Rewrites the gaps between tokens according to a rules file and leaves everything no active rule governs exactly as written. It uses the lexer, never the parser, and it emits the result line by line.

Say it like this

"The formatter never builds a tree. It lexes the source and, for every gap between two tokens, decides what should go there. If an active rule covers that gap, the rule decides: spaces around =, a line break after a println, the indent inside an if. If no rule does, the gap is copied from the source unchanged. That's what the TCK expects: turn on one rule and only that rule's gaps change. The config is YAML or JSON, read by one parser, and a missing rule means 'don't touch'. Output comes out one line at a time, so large files work too."

Gaps, not trees

The one idea the whole module is built on.

The TCK's formatter cases enable one rule per config file and expect the rest of the source untouched. Two declarations can end up with different spacing before : when only the "space after colon" rule is on. A tree has already thrown away how the source was spaced, so reprinting from it would normalise everything. Token positions still hold that information (TokenFormatter.kt:6–15).

The main loop

Recover the original text of every token, then walk the tokens in pairs.

  • A separator can contain line breaks. Each \n in it finishes the current output line and yields it (:40–46). That's how output leaves one line at a time.

Laziness, measured

2 lines

read before the first output line appears, from an infinite source. A line is finished only when the separator before the next token, on the next line, is known.

1,001

lines read to produce 1,000 output lines. The lookahead stays at exactly one line; the source is never loaded as a whole.

Deciding a gap

An explicit priority order, from the most specific rules to the broadest.

59    private fun separatorBetween(60        previous: SourceToken,61        next: SourceToken,62        state: FormattingState,63    ): String {64        val brokeLine = next.startRow > previous.endRow6566        bracePlacement(next, state)?.let { return it }67        if (previous.isSemicolon) {68            breaksAfterStatement(state, brokeLine)?.let { breaks ->69                return newline(breaks, indentFor(next, state, useOriginal = brokeLine))70            }71        }72        if (brokeLine) {73            return newline(next.startRow - previous.endRow, indentFor(next, state, useOriginal = true))74        }75        return spacingBetween(previous, next, state)76    }

  • Colon rules only inside a declaration (:138–139). FormattingState.inDeclaration is true only for statements that start with let or const.
  • Single-space separation goes last (:148) because it's the broadest: any more specific rule for this gap has already decided. It puts one space in every gap except before ;.
  • The fallback is the source (:150): the original column distance between the two tokens.

Braces and indentation (1.1)

Without a parser, the formatter reconstructs just enough structure by counting.

Decisions to defend

Each with the cost we accepted.

Rewrite the gaps between tokens instead of reprinting the AST

A rule that isn't on must leave the source as written, and only the tokens' positions still contain that information. It also matches the TCK's one-rule-per-file cases exactly.

CostEvery rule must be expressed as a decision about a single gap. Structural rewrites (moving statements, splitting expressions) aren't possible, and none are required.

Depend on the lexer, not the parser

The formatter can format code that doesn't parse yet, the way an editor would, it streams line by line, and it avoids building nodes it would throw away.

CostIt isn't a validator: let x: number = = 5; formats without complaint. FormattingState has to rebuild a little structure by counting braces.

A missing rule means "don't touch"

The TCK gives one rule per config and expects nothing else to change. Three-state settings also merge the two spellings of the = rule and of the brace rule into one field each.

CostNo defaults: a config has to name every rule it wants, and an empty config formats nothing.

An explicit order when rules compete for the same gap

A colon gap is covered by both the colon rule and single-space separation. Checking specific rules first and the broadest last (TokenFormatter.kt:146–148) makes the outcome predictable.

CostAdding a rule means choosing where it goes in separatorBetween and spacingBetween. The order is part of the behaviour.

One YAML parser for both YAML and JSON

The assignment allows either format, and JSON is valid YAML, so a single library and code path handle both.

CostA ".json" file with YAML-only syntax is accepted too. That's lenient, but harmless.

Stream output lines, with one line of lookahead

formatLines is part of the interface (Formatter.kt:8–15), so any caller can format a file larger than memory, and the CLI does.

CostA line is emitted only after the next line's first token is read (2 lines read for the first output line). SourceScanner also relies on the lexer finishing a line before reading the next, an implicit contract documented at SourceToken.kt:33–38.

Questions you might get

Short answers, with the line to show.

Why isn't the formatter built on the parser's AST?

Because rules that aren't active must leave the source untouched, and the AST has no spacing information. Gallery case 2 shows it: only the "after colon" gaps change, and the second declaration keeps its space before the colon.

How can it indent blocks without parsing?

It counts { and } as tokens go by (FormattingState.kt:39–51). Indent is size × depth, one level less for a closing brace. For layout, depth is all it needs.

What if a config turns on both enforce-spacing-around-equals and enforce-no-spacing-around-equals?

They're one setting, so they can't both apply. The "spacing" check comes first and wins (FormattingRules.kt:57–62). Brace placement works the same way: same line wins over below.

Why does single-space separation give println ( x )?

The rule is "exactly one space between tokens", and parentheses are tokens. The only exception is before ; (TokenFormatter.kt:148). In practice it's combined with other rules; on its own it applies literally.

Why SnakeYAML here and Jackson in the linter?

The formatter reads a free-form map of rule names, and one YAML parser covers both formats. The linter binds a fixed JSON shape to a typed class, which is what Jackson is for. Using one library for both would be a reasonable cleanup; the choice follows what each module's config needs.

Does the formatter report syntax errors?

Only lexical ones: an invalid character like @ still throws a positioned LexerException, because the formatter uses the lexer. Grammar errors are the validation operation's job.

How does 1.1 code with braces get formatted under version 1.0?

It doesn't: the builder creates a lexer for the requested version (FormatterBuilderPS.kt:24), and the 1.0 lexer rejects {. The version controls the formatter the same way it controls every other tool.
