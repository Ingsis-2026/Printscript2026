Say it like this

"The formatter never builds a tree. It lexes the source and, for every gap between two tokens, decides what should go there. If an active rule covers that gap, the rule decides: spaces around =, a line break after a println, the indent inside an if. If no rule does, the gap is copied from the source unchanged. That's what the TCK expects: turn on one rule and only that rule's gaps change. The config is YAML or JSON, read by one parser, and a missing rule means 'don't touch'. Output comes out one line at a time, so large files work too."

Gaps, not trees

The one idea the whole module is built on.

The TCK's formatter cases enable one rule per config file and expect the rest of the source untouched. Two declarations can end up with different spacing before : when only the "space after colon" rule is on. A tree has already thrown away how the source was spaced, so reprinting from it would normalise everything. Token positions still hold that information (TokenFormatter.kt:7–17).

The main loop

Recover the original text of every token, then walk the tokens in pairs and write each gap.

SourceToken.kt

  • Why keep text (:15)? The lexer strips the quotes from string values, but the formatter has to write "hi" back exactly as it was.
  • It answers questions instead of handing out its token (:17–27): the type and the value stay inside. The lexer scans one line at a time, so a token never spans lines and has a single row (:19). A declaration starts with a KEYWORD (:26), which in every version means exactly let and const. println also needs its text (:27), because readInput and readEnv are FUNCTIONs too.
  • Punctuation is recognised by its type as well as its text (:29–35). Without quotes, the string in println(";") has the value ;, just like the semicolon that ends the statement. The parser checks the same way (TokenRoles.kt:32).

12internal class SourceScanner(13    private val lexer: Lexer,14) {15    fun scan(lines: Sequence<String>): Sequence<SourceToken> =16        sequence {17            var lastLineRead = ""18            val remembered = lines.onEach { lastLineRead = it }1920            for (token in lexer.convertToTokens(remembered)) {21                val text = lastLineRead.substring(token.getPosition().column, token.getFinalPosition().column)22                yield(SourceToken(token, text))23            }24        }25}
  • Only one line is remembered (:17–18). onEach looks at each line as the lexer pulls it, without changing it. The lexer emits all tokens of a line before reading the next one, so the last line read is always the line the current tokens came from.
  • substring(start, end) (:21) cuts each token's original text out of that line.

  • For each token, decide the Gap from the previous token (:34). The first token gets its original leading blank lines and indent (:44).
  • Writing is someone else's job (:35): OutputLines takes the gap and the token's text and returns the lines that are now complete, which are passed on right away with yieldAll. That's how output leaves one line at a time.

Laziness, measured

2 lines

read before the first output line appears, from an infinite source. A line is finished only when the gap before the next token, on the next line, is known.

1,001

lines read to produce 1,000 output lines. The lookahead stays at exactly one line; the source is never loaded as a whole.

Deciding a gap

One when, from the most specific rule to the broadest. The first branch that holds decides.

Gap.kt

7internal data class Gap(8    val breaks: Int,9    val spaces: Int,10) {11    companion object {12        fun sameLine(spaces: Int): Gap = Gap(breaks = 0, spaces = spaces)1314        fun lineBreaks(15            breaks: Int,16            indent: Int,17        ): Gap = Gap(breaks = breaks, spaces = indent)18    }
  • A gap is a value (:7–10): how many line breaks, then how many spaces. After a break, the spaces are the new line's indent.

TokenFormatter.kt

46    /** Las reglas van de la más puntual a la más amplia, así que la primera que aplica decide. */47    private fun gapBetween(48        previous: SourceToken,49        next: SourceToken,50        state: FormattingState,51    ): Gap {52        val sourceBreaks = next.row - previous.row53        val indent = if (sourceBreaks > 0) indentation.forSourceBreak(next, state) else indentation.forAddedBreak(next, state)54        val bracePlacement = if (next.isOpeningBrace) rules.bracePlacement else null55        val blankLinesAfterPrintln = rules.blankLinesAfterPrintln56        val endsPrintln = previous.isSemicolon && state.statement == StatementKind.PRINTLN57        return when {58            bracePlacement == BracePlacement.SAME_LINE -> Gap.sameLine(1)59            bracePlacement == BracePlacement.NEXT_LINE -> Gap.lineBreaks(1, indentation.forAddedBreak(next, state))60            blankLinesAfterPrintln != null && endsPrintln -> Gap.lineBreaks(blankLinesAfterPrintln + 1, indent)61            rules.lineBreakAfterStatement && previous.isSemicolon && sourceBreaks == 0 -> Gap.lineBreaks(1, indent)62            sourceBreaks > 0 -> Gap.lineBreaks(sourceBreaks, indent)63            else -> Gap.sameLine(spacesBetween(previous, next, state))64        }65    }

Kotlin takes the first branch that holds, so reading the when top to bottom is reading the precedence. Rules that depend on each other say so in their condition: the line-break rule only adds a break where the source had none (sourceBreaks == 0, :61), and anywhere else branch 5 keeps the source's breaks.

The indent is chosen once, by who made the break (:53): forSourceBreak if the source already had it, forAddedBreak if the formatter is adding it. A brace moved below always counts as added (:59). bracePlacement is only set when the next token is a { (:54), so branches 1 and 2 don't need to check that again.

  • Same precedence idea, for spaces: the first condition that holds decides the number of spaces.
  • Colon rules only inside a declaration (:72, :75–76): the statement has to be a StatementKind.DECLARATION, meaning it starts with let or const.
  • The = setting is already the number of spaces (:77), so there's nothing to translate.
  • Single-space separation goes last (:79) because it's the broadest: any more specific rule for this gap has already decided. It puts one space in every gap except before ;.
  • The fallback is the source (:80): the original column distance between the two tokens.

Line breaks. "n blank lines after a println" is blankLinesAfterPrintln + 1 line breaks (:60). It applies after a ; whose statement is a PRINTLN (:56). A ; belongs to the statement it closes, so the state still names that statement (FormattingState.kt:7–8). "A line break after every statement" adds one only where the source had none (:61), so existing blank lines are kept by branch 5.

  • Three facts, no tree: the brace depth, the statement of the last token read, and the indent of the current line.
  • A statement's kind comes from its first token (:26), and that's all the rules ever ask about a statement (StatementKind.kt:15–20).

Decisions to defend

Each with the cost we accepted.

Rewrite the gaps between tokens instead of reprinting the AST

A rule that isn't on must leave the source as written, and only the tokens' positions still contain that information. It also matches the TCK's one-rule-per-file cases exactly.

CostEvery rule must be expressed as a decision about a single gap. Structural rewrites (moving statements, splitting expressions) aren't possible, and none are required.

Depend on the lexer, not the parser

The formatter can format code that doesn't parse yet, the way an editor would, it streams line by line, and it avoids building nodes it would throw away.

CostIt isn't a validator: let x: number = = 5; formats without complaint. FormattingState has to rebuild a little structure by counting braces.

A missing rule means "don't touch"

The TCK gives one rule per config and expects nothing else to change. Nullable settings also merge the two spellings of the = rule and of the brace rule into one field each.

CostNo defaults: a config has to name every rule it wants, and an empty config formats nothing.

An explicit order when rules compete for the same gap

A colon gap is covered by both the colon rule and single-space separation. Checking specific rules first and the broadest last makes the outcome predictable, and the order is written down literally: the when in gapBetween (TokenFormatter.kt:57–64) and the one in spacesBetween (:74–81).

CostAdding a rule means choosing its place in one of those whens. The order is part of the behaviour.

One YAML parser for both YAML and JSON

The assignment allows either format, and JSON is valid YAML, so a single library and code path handle both.

CostA ".json" file with YAML-only syntax is accepted too. That's lenient, but harmless.

Stream output lines, with one line of lookahead

formatLines is part of the interface (Formatter.kt:6–12), so any caller can format a file larger than memory, and the CLI does.

CostA line is emitted only after the next line's first token is read (2 lines read for the first output line). SourceScanner also relies on the lexer finishing a line before reading the next, an implicit contract documented at SourceScanner.kt:5–11.

Questions you might get

Short answers, with the line to show.

Why isn't the formatter built on the parser's AST?

Because rules that aren't active must leave the source untouched, and the AST has no spacing information. Gallery case 2 shows it: only the "after colon" gaps change, and the second declaration keeps its space before the colon.

How can it indent blocks without parsing?

It counts { and } as tokens go by (FormattingState.kt:29–30). Indent is size × depth, one level less for a closing brace (:17–18). For layout, depth is all it needs.

What if a config turns on both enforce-spacing-around-equals and enforce-no-spacing-around-equals?

They're one setting, so they can't both apply. The "spacing" check comes first and wins (FormattingRules.kt:55–60). Brace placement works the same way: same line wins over below.

Why does single-space separation give println ( x )?

The rule is "exactly one space between tokens", and parentheses are tokens. The only exception is before ; (TokenFormatter.kt:79). In practice it's combined with other rules; on its own it applies literally.

Why SnakeYAML here and Jackson in the linter?

The formatter reads a free-form map of rule names, and one YAML parser covers both formats. The linter binds a fixed JSON shape to a typed class, which is what Jackson is for. Using one library for both would be a reasonable cleanup; the choice follows what each module's config needs.

Does the formatter report syntax errors?

Only lexical ones: an invalid character like @ still throws a positioned LexerException, because the formatter uses the lexer. Grammar errors are the validation operation's job.

How does 1.1 code with braces get formatted under version 1.0?

It doesn't: the builder creates a lexer for the requested version (FormatterBuilderPS.kt:25), and the 1.0 lexer rejects {. The version controls the formatter the same way it controls every other tool.

What if a string contains a ; or a brace?

It stays a string. The lexer drops the quotes, so the string in println(";") has the value ;. That's why punctuation is recognised by its token type as well as its text (SourceToken.kt:29–35), the same check the parser does. FormatterEdgeCaseTest covers ;, { and } inside strings.

Why is the gap decision one when and not one class per rule?

Because the order is part of the behaviour, and the rules depend on each other. With one class per rule, the order lived in a list somewhere else, and one rule handed a gap to the next by returning null, which only a comment explained. In a when, the branches read top to bottom as the precedence, and each hand-off is a condition you can point at, like sourceBreaks == 0 (TokenFormatter.kt:61). The parser's list of factories is different: each factory decides on its own.
