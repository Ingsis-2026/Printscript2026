Say it like this

"commons is the vocabulary every module shares. A token is a type, its text, and where it starts and ends in the file. The AST is a sealed class with nine node types, and every node knows its position. PrintScriptException is the single error type: the lexer, parser and interpreter each throw a subclass, and it carries the location as data. Because these types live here, the parser and the interpreter depend on commons and nothing else. They never import each other."

Read it as a pipeline. The lexer is the only module that creates tokens and positions (Lexer.kt:81–87), and the parser is the only one that creates AST nodes. Everything downstream only reads them. The interpreter "reads" Token through BinaryNode.operator. Errors run the other way: three modules throw them, and the CLI catches them in one place (PrintScriptCli.kt:29). The TCK adapter catches them the same way (Pipeline.java:42).

  • sealed class (:7). All subclasses must live in this module, so the compiler knows the complete list. A when (node) without else won't compile if a type is missing, and the linter's walks rely on exactly that (Statements.kt:74).
  • abstract val position (:8). Every node must say where it is. That's what lets the interpreter attach a location to a run-time error without knowing which node kind failed (Interpreter.kt:40).
  • ConditionalNode.condition is a LiteralNode (:52), not any ASTNode. The 1.1 spec allows only a boolean variable as the if argument, and the type makes if (a + b) impossible to represent.

14abstract class PrintScriptException(15    message: String,16    val startPosition: TokenPosition? = null,17    val endPosition: TokenPosition? = null,18) : RuntimeException(message) {19    /** Mensaje con la ubicación en coordenadas 1-based, para mostrar al usuario. */20    fun describe(): String {21        val text = message ?: ""22        val location = locationText() ?: return text23        return "$text ($location)"24    }2526    private fun locationText(): String? {27        val start = startPosition ?: return null28        val end = endPosition ?: start29        if (start == end) return "línea ${start.row + 1}, columna ${start.column + 1}"30        return "desde línea ${start.row + 1}, columna ${start.column + 1} " +31            "hasta línea ${end.row + 1}, columna ${end.column + 1}"32    }33}
  • abstract: you always throw a specific stage's error, LexerException, ParserException or InterpreterException, each a 5-line subclass in its own module. Catching the base class catches all three.
  • Position as data, not text (:16–17). message stays clean for tests, and each front end decides how to show the location.
  • describe() (:20) is the single place that converts to 1-based coordinates. It prints one point when start equals end (:29) and a "desde … hasta …" range otherwise (:30–31). A missing end falls back to the start (:28), and no position at all returns just the message (:22).
  • What the user sees: Error: Const declarations are not allowed in version 1.0 (desde línea 1, columna 1 hasta línea 1, columna 6).

Decisions to defend

Each with the cost we accepted, because graders ask "why not the alternative?"

A shared types module, exposed with api instead of implementation

Our public signatures mention these types, for example Parser.execute(tokens: Sequence<Token>): Sequence<ASTNode> (Parser.kt:21). Anyone calling the parser needs Token and ASTNode on their compile classpath, and api passes them along automatically. Without it, every consumer would have to declare commons again just to call the parser.

CostEvery module recompiles when commons changes, which is acceptable because it changes only when the language itself does.

A sealed AST

The language is meant to grow. With a sealed class, adding a construct produces compile errors in every exhaustive when that must handle it, instead of silently doing nothing.

CostAll nodes must live in commons, so no module can define its own node types. For a language with one official AST, that's the point.

Immutable tokens that carry a start and an end position

The required error format needs both ends of a range, and immutability makes tokens safe to compare, store and share between stages.

CostTwo more objects per token. At the TCK's 7 MB heap that's fine, because tokens are discarded statement by statement.

One unchecked base exception with the position as data

Errors surface inside lazy sequences (the lexer throws while the interpreter is pulling nodes), and a checked exception couldn't be declared through Sequence.map lambdas; Kotlin has no checked exceptions anyway. One base type means one catch per front end, which is the Liskov substitution principle in practice.

CostOnly the first error is reported, and the interpreter's errors have a start position but no end, because nodes store a single position (InterpreterException.kt:9–11).

A null object instead of ASTNode?

NilNode means "nothing here" without nullable fields spreading through the parser and interpreter. It even has its own evaluator (NilEvaluator.kt:13), so "no value" goes through the same dispatch as everything else.

CostA reader has to learn what NilNode means before the AST reads clearly, and every exhaustive when carries a branch for it. In exchange no field in the AST is nullable: ConditionalNode.elseBlock (ASTNode.kt:55) defaults to it, so "no else" is written one way.

Questions you might get

Short answers, with the line to show.

Why does Token use getType() while value is a property?

It's a style inconsistency with no effect on behaviour. A Kotlin val type compiles to the same getType() for Java callers like the TCK. Owning it is better than inventing a reason.

If declType is always KEYWORD, why store it?

The node mirrors the token's (type, value) pair, and only the value is used: declValue is "let" or "const", which the interpreter reads to block reassigning a const (DeclarationEvaluator.kt:33). The same goes for AssignationNode.valType. Removing those fields would be a safe simplification.

Why are positions nullable in the exception?

Some errors have no token at hand. An empty file fails with "No valid code" (StatementSplitter.kt:90), and there's no position to give. describe() handles that case (:22).

Why doesn't commons contain the lexer's token rules?

What a token is is shared; how to recognise one is lexer behaviour and changes per version (TokenMapper.kt:19–24). Keeping behaviour out is what lets the parser depend on commons without depending on the lexer.
