The big picture

PrintScript is a chain of lazy Kotlin Sequences. The source is read one line at a time. The lexer turns each line into tokens, and the parser groups tokens into one statement at a time and builds one AST node per statement. Then a consumer does something with each node before the next one is read: the interpreter runs it, the linter checks it, and the CLI's validation mode just counts it. The formatter is the exception. It works on the lexer's tokens directly and never builds an AST.

A presentation order that works

Open with these two figures, then walk the assignment's own Example 2 through the pipeline (next section). The graders know that program and its expected output, so every stage has something concrete to show. Streaming, versioning and error positions come up naturally along the way: name them as they appear, then cover each module in depth, and keep the "decisions under challenge" section for the questions.

Parser: four statements, four nodes

The splitter emits a statement at each ; (StatementSplitter.kt:79–84). The parser then asks each factory in turn whether it can handle the statement (Parser.kt:49). For let c: number = a / b, PrintlnFactory says no because the first token isn't println, and DeclarationFactory says yes because there's a KEYWORD token. In version 1.0 there is no ConditionalFactory in the list to ask first. The declared type is number and the expression has no string or boolean literals, so the static check passes (DeclarationFactory.kt:66–69). For the last statement, PrintlnFactory matches.

The printer receives Result: 3, which is exactly the output the PDF expects. In the CLI the printer is OutputPrinter writing to stdout; in the TCK it's the test's PrintEmitter. The interpreter code is identical in both.

Linter: the same nodes, read as they are

DeclarationNode a   @0:4    identifier a                  @0:4

The linter reads the very same nodes the interpreter just ran — nothing is converted first. The identifier rules ask where the names are; the println rule asks one question about one node, is the argument a BinaryNode or another call. With snake case and the println rule on, all identifiers pass and the last statement is flagged, "Println must not be called with an expression" at 4,0, which the user sees as línea 5, columna 1. So the assignment's own example violates that rule, and it makes a good live demo.

commons

no dependencies · consumed via api(project(":commons"))

This module holds the shared vocabulary: tokens, positions, the AST and the base error type. It contains no behaviour beyond error formatting. Every other module declares it with api, so anything that depends on the lexer also gets Token without declaring it again.

What's in it

  1. Tokens. TokenType.kt:3 lists 14 categories (IDENTIFIER, KEYWORD, DATA_TYPE, FUNCTION, CONDITIONAL…), each one the lexer can emit. TokenPosition.kt:3 is a 0-based (row, column). Token.kt:7–12 is an immutable data class carrying both a start and an end position. Having the end position is what lets errors report the full range the assignment asks for (Token.kt:17–21).
  2. The AST. ASTNode.kt:7 is a sealed class in which every node has a position. There are nine node types: LiteralNode :11, BinaryNode :17, PrintNode :24, DeclarationNode :29, AssignationNode :39, BlockNode :46, ConditionalNode :51, FunctionNode :58, and NilNode :66, a null object used for "no value". ConditionalNode.condition is typed LiteralNode, which encodes the 1.1 rule that an if takes only a boolean variable or literal.
  3. Errors. PrintScriptException.kt:14–18 is an abstract RuntimeException with optional start and end positions. describe() at :20 converts to 1-based coordinates and prints "desde línea X, columna Y hasta línea …", or a single point when start equals end (:29). LexerException, ParserException and InterpreterException all extend it.

Decisions to defend

Position travels as data, not inside the messagePrintScriptException.kt:8–11
Tests can compare clean messages, and each front end formats the location its own way: the CLI in Spanish, the TCK adapter as-is. The CLI catches a single exception type and never needs to know which stage failed (PrintScriptCli.kt:29).
Sealed ASTASTNode.kt:7
The compiler checks every exhaustive when, so a new language construct can't be silently ignored by a consumer. This matters because the assignment says the language will grow.
A shared module instead of duplicating types*/build.gradle.kts
This gives low coupling: tools depend on a small, stable contract rather than on each other. Parser and interpreter need nothing else (Figure 2).

Trade-offs to own

  • Why one exception type with nullable positions? Some errors have no token at hand, such as an empty program (StatementSplitter.kt:97). Nullable positions let those share the same hierarchy instead of needing a second error type.

lexer

depends on commons

The lexer turns text into a lazy stream of Tokens, rejecting any character it can't classify and any keyword the chosen version doesn't allow, each with an exact position.

Step by step

  1. Pick the vocabulary for the version. TokenMapper.kt:10–13 builds a mapper from a version string, and TokenMapper.kt:74–86 selects the regex strategies and the "disallowed" keywords. 1.0 disallows const with a message (:83).
  2. Compile one big regex. Lexer.kt:14 calls PatternMatcher.kt:9–17, which joins every strategy's pattern into a single alternation (p1)|(p2)|…. Order matters here: mapOf preserves insertion order, so let is tried before IDENTIFIER and = (ASSIGNATION) before the general OPERATOR class.
  3. Stream the lines. Lexer.kt:29–39 wraps the loop in sequence { … yield(token) }, so a line is read only when the parser asks for tokens past the previous one. The InputStream overload (:41–44) wraps a BufferedReader.lineSequence().
  4. Match inside a line. Lexer.kt:54–72 loops over matcher.find(), taking the start and end positions from the match (:58–59).
  5. Catch what the regex skipped. Matcher.find doesn't fail on garbage; it just jumps past it. Lexer.kt:85–103 inspects the gap before each match (:55) and the tail of the line (:73), and any non-blank text in those gaps becomes "Carácter inválido encontrado" with its exact columns.
  6. Version gate, then classify. Lexer.kt:62 asks disallowedReason and throws a positioned LexerException. TokenMapper.kt:24–30 checks reserved words first (:35–44), then the first strategy that matches, and UNKNOWN produces an error at :65–67.
  7. Clean the value. Lexer.kt:105–112 strips the quotes from string literals. The formatter needs those quotes back, which is why it keeps the original text (see formatter).

1.0 vs 1.1

TokenMapper.kt:61–70 copies the 1.0 map and adds if/else, const, readInput/readEnv, boolean, true/false and the { } punctuators. Because braces aren't in the 1.0 vocabulary, an if program under 1.0 fails right in the lexer. I checked this by running it, and it prints Carácter inválido encontrado: '{'.

Decisions to defend

Strategy pattern for token kindsTokenClassifierStrategy.kt:3 · RegexTokenClassifier.kt:3
A new token kind is a new map entry, and Lexer itself doesn't change (Open/Closed). A version is just a different map.
Lazy, line-granular lexingLexer.kt:29
Memory is bounded by the longest line, not by the file. This is what lets the TCK's 131,072-line test run in a 7 MB heap.
The version check lives in the lexer, not in classifyTokenMapper.kt:15–21
Only the lexer knows where the lexeme is, so rejecting const there produces an error with row and column instead of a generic one.

Trade-offs to own

  • Order-sensitive alternation. The combined regex tries patterns in map order, so = must come before the general operator class and number before identifiers. We accept this because the map is the single place to look, and the Example 2 trace shows each case resolving correctly.
  • Classification is a second, simple pass (TokenMapper.kt:24–30): reserved words first, then the first matching strategy. Reading regex group indices would be faster, but it would couple the lexer to the order in which groups were built. Clarity was worth a few extra regex tests per token.

Tests: 21 in LexerTests and TokenMapperTest.

parser

depends on commons (lexer only in tests)

The parser groups the token stream into statements and turns each one into an AST node. It does this in two parts: a state machine that decides where a statement ends, and a list of factories that each know how to build one kind of statement.

Step by step

  1. Choose factories for the version. ParserFactory.kt:20–42: the 1.0 list is Println, Declaration, Assignation and Function, and 1.1 puts ConditionalFactory first. The language version comes down to which factories are in the list.
  2. Stay lazy. Parser.kt:21 calls StatementSplitter().split(tokens) and then .map { createNode(it) }, so a statement is only parsed when someone asks for the next node.
  3. Cut statements (the state machine). In StatementSplitter.kt:23–98, ; ends a statement (:79–84), but only outside braces: openBraces is counted at :45–54 so the ;s inside a block stay together. When a block closes, the statement is held back one token in case an else follows (:33–42). An if must start a fresh statement (:73–77), a stray } is an error (:66), and the stream can't end mid-statement (:90–95). An empty program is rejected (:97).
  4. Pick a factory (chain of responsibility). Parser.kt:49 takes the first factory whose canHandle returns true. If none does, it throws "Can't handle this sentence" with the statement's range (:39–45).
  5. Build the node. Each factory is described below.
FactoryHow it builds
DeclarationFactory.kt:12Finds the keyword, identifier and type (:13–21). The expression is everything after = (:23–26). It does a static literal-vs-type check (:60–90), skipped when the value is a readInput/readEnv call because the type isn't known until run time (:29–34). The node's position is the identifier (:43).
AssignationFactory.kt:12The left side is the tokens before = (:61), the right side the tokens after (:59). The right side goes to FunctionFactory or OperationFactory (:63–68).
PrintlnFactory.kt:10Needs at least 4 tokens (:45–46). Takes what's between the first ( and the last ) (:15–22) and passes it to OperationFactory (:28).
FunctionFactory.kt:9readInput/readEnv: the argument is the tokens between the parentheses (:12), parsed as an expression (:16).
OperationFactory.kt:10Handles precedence by splitting the expression. It tries + - first (:22), then * / (:23), which puts the lower-precedence operator at the root of the tree. Operators inside parentheses are skipped (:36–54), and fully wrapping parentheses are removed (:56–65).
ConditionalFactory.kt:16Reads the condition token after ( (:33–40), then finds the matching } by counting depth (:111–126). The block body goes to a sub-parser (:64–74), which is how nested ifs work. The else must immediately follow the then-block (:82–94), and else if is rejected (:90–92).

How precedence falls out of splitting

// OperationFactory.kt:22–23: the lowest precedence becomes the root
return splitOnOperator(tokens, ::isAdditionOrSubtraction)
    ?: splitOnOperator(tokens, ::isMultiplicationOrDivision)
    ?: throw ParserException("Error in operation", …)

2 + 3 * 4 splits at +, so the tree is 2 + (3 * 4) and the result is 14. Parentheses work the same way: the operators inside them are skipped at this level, then the outer pair is removed and the inner expression is split again.

Decisions to defend

Factories + chain of responsibilityASTFactory.kt:6 · Parser.kt:49
Adding a construct means adding a factory and listing it for its version, with no edits to Parser. Each factory has one job (SRP).
Splitting separated from buildingStatementSplitter.kt:20
The splitter only answers "where does this statement end?", and factories only see complete statements. It's also the only place memory has to be reasoned about: the current statement is all that's held (:8–11).
Sub-parser injected as a providerConditionalFactory.kt:14 · ParserFactory.kt:34
A block body is parsed by a fresh parser for the same version, which gives recursion for nested blocks. Tests can inject a fake parser.
insideBlock modeParser.kt:33 · StatementSplitter.kt:58–64
In a block body, the closing } terminates the last statement. At top level, the same } is an error.

Trade-offs to own

  • Factories choose by the tokens they see, not by a grammar. Each canHandle is one line, so factories stay independent of each other. The cost is that list order matters: ConditionalFactory goes first because an if block contains declarations and assignments too (ParserFactory.kt:34–38).
  • Expressions are parsed by splitting, not by grammar rules. For PrintScript's four operators and parentheses, that's about 60 lines with no parser generator. A new precedence level is one more splitOnOperator call in the chain.

Tests: 61, including BlockParsingTest, StreamingPipelineTest, PositionedErrorTest and one test class per factory.

interpreter

depends on commons (lexer, parser only in tests)

The interpreter executes one AST node at a time against a symbol table. Output and input go through two one-method interfaces, so the same interpreter runs in the CLI (stdout/stdin) and in the TCK (its emitter and input provider).

Step by step

  1. Choose evaluators for the version. InterpreterFactory.kt:14–47: version10Evaluators() is the 1.0 list, and version11Evaluators() is written as that list plus what 1.1 adds — ConditionalEvaluator and FunctionEvaluator (:34).
  2. Hold state. Interpreter.kt:11–15 keeps one VariableTable, which stores each variable's Declaration (the keyword, to reject reassigning a const, and the declared type, to type a later readInput) separately from its value — because a variable can be declared without a value, and can get a value without being declared.
  3. Dispatch and position errors. Interpreter.kt:25–35 finds the evaluator that canEvaluate the node and runs it. Evaluators throw errors without positions; the catch at :38–40 adds node.position only if the error has none yet, so the reported location is the innermost node that failed.
  4. Literals. LiteralEvaluator.kt:17–34: a number becomes Int if possible, otherwise Double (:19). An identifier is looked up and throws "Undefined variable" if missing (:30–32).
  5. Binary operations. BinaryEvaluator.kt:19–27 dispatches on the operator, one named operation per branch. + tries string concatenation first (:30–36), which is how "Result: " + 3 becomes a string. Numeric promotion between Int and Double is one when of two cases in ArithmeticOperations.kt:24–36. Division by zero is checked at :115–117, and multiplying or dividing a string is rejected at :47–49 and :57–59.
  6. Declarations. DeclarationEvaluator.kt:18–44 rejects a name that is already taken (:19–21) and records the Declaration even when there's no value (:32–35). It types an ExternalInput using the declared type (:38).
  7. Assignments. AssignmentEvaluator.kt:17–27 refuses to reassign a const (:48–51) and refuses a value of a different PrintScript type (:55–58). Int and Double both count as number.
  8. println, if, blocks. PrintEvaluator.kt:16–23 prints through the injected Printer. ConditionalEvaluator.kt:16–29 requires a Boolean (:18–20). BlockEvaluator.kt:16–18 runs children in order, and NilEvaluator returns null.
  9. readInput / readEnv. FunctionEvaluator.kt:33–42 prints the prompt, then asks the Reader. readEnv reads System.getenv (:44–51). Both return an ExternalInput, not a typed value.

The typed-input trick

// ExternalInput.kt:10–21: the destination decides the type
fun asType(dataType: String): Any = when (dataType) {
    "string"  -> text
    "number"  -> text.toIntOrNull() ?: text.toDoubleOrNull() ?: throw cannotInterpretAs(dataType)
    "boolean" -> when (text) { "true" -> true; "false" -> false; else -> throw cannotInterpretAs(dataType) }
    else      -> throw InterpreterException(…)
}

The 1.1 spec says readInput returns a type compatible with the variable it's assigned to, or string inside println, and that execution fails if, say, "Hola" arrives for a boolean. So the raw text travels until someone who knows the target type converts it: the declaration (:36), the assignment (AssignmentEvaluator.kt:33–43) or println (PrintEvaluator.kt:20). The doc comment at ExternalInput.kt:3–11 records the earlier bug this fixed: a 5 typed into a string variable used to become a number.

Decisions to defend

One evaluator per node typeNodeEvaluator.kt:6 · InterpreterFactory.kt:16
This is a strategy registry: a new node type is a new evaluator plus a list entry, with no edits to Interpreter. The version is again just the list.
Printer / Reader interfacesPrinter.kt:3 · Reader.kt:3
Dependency inversion. The spec requires a programmatic way to provide input, which is the TCK's InputProvider. Being single-method interfaces, they take Java method references directly (InterpreterAdapter.java:54).
Executes node by nodeInterpreter.kt:32
The interpreter never sees the whole program, and the caller decides how the stream is fed. That's what lets execution interleave with parsing.

Tests: 126, including SpecComplianceTest, ExternalInputTypingTest, AssignmentTypeTests and PositionedRuntimeErrorTest.

formatter

depends on commons, lexer · snakeyaml 2.0

The formatter rewrites the gaps between tokens according to a rules file and leaves everything no active rule governs exactly as it was written. It uses the lexer but never the parser.

Why not reprint the AST?

The TCK's formatter cases turn on one rule at a time and expect the rest of the file untouched. For example, two declarations can keep different spacing before : when only the "space after colon" rule is on. The AST has already discarded how the source was written, so reprinting from it can't do that. Token positions still carry that information. See the doc comment at TokenFormatter.kt:6–15 and commit 2321eb3, "formatear preservando el fuente en lugar de reimprimir el árbol".

Step by step

  1. Read the rules. RulesReader.kt:16–31 parses YAML and JSON with SnakeYAML, since JSON is a subset of YAML. Anything that isn't a key/value map is rejected (:26–28).
  2. Map config names to settings. FormattingRules.kt:24–34 holds the TCK's rule names, and from (:36–47) builds the settings. A missing key means "don't touch" (:3–9). The two = rules collapse into a three-state Boolean? (:57–62), as do the two brace rules (:64–69).
  3. Build. FormatterBuilderPS.kt:21–24 creates TokenFormatter(rules, Lexer(TokenMapper(version))). Overloads accept a path (:10) or an InputStream (:16).
  4. Recover the original text. SourceToken.kt:40–53 pairs each token with its exact source slice. It remembers only the line currently being lexed (:45–46), which works because the lexer emits all of a line's tokens before reading the next line.
  5. Walk token pairs. TokenFormatter.kt:30–54 computes the separator between the previous and current token. If the separator contains newlines, the finished line is emitted (:40–46). Then FormattingState advances (:49).
  6. Decide a gap, in priority order. TokenFormatter.kt:59–76: brace placement (:66), then breaks after ; (:67–71), then line breaks already in the source (:72–74), then same-line spacing (:75).
  7. Same-line spacing. TokenFormatter.kt:133–151: colon rules only apply inside a declaration (:138–139), then = (:141–143), then operators (:144). Single-space separation goes last because it's the broadest rule (:146–148). With no rule active, the original gap is preserved (:150).
  8. Indentation. TokenFormatter.kt:115–125: with indent-inside-if set, indent = n × depth, and a closing brace is one level out (:121). Otherwise the source's own column is kept. FormattingState.kt:27–52 tracks depth, whether we're inside a declaration, and whether the current statement is a println.
  9. Blank lines after println. TokenFormatter.kt:96–104: n blank lines means n + 1 line breaks.

Decisions to defend

Preserve the source, rewrite only governed gapsTokenFormatter.kt:6–15
This matches what the TCK expects rule by rule, and it's the least surprising behaviour for a user: turning on one rule changes only what that rule governs.
Three-state settingsFormattingRules.kt:13–21
true enforces the rule, false enforces the opposite, and null leaves the source alone. Two config keys become one field, so the two can't contradict each other.
Lazy line emissionFormatter.kt:8–15
formatLines is part of the interface so that any caller can format a file too large for memory. The CLI uses it (FormattingCommand.kt:21).

Trade-offs to own

  • "Not configurable" rules became configurable. The 1.0 spec lists single spacing, spaces around operators and a break after ; as fixed. The TCK's config names them as rules, so we implemented them as rules whose absence leaves the source unchanged. That satisfies both documents.
  • The formatter doesn't validate syntax. Its job is layout, and validation is its own CLI operation. Needing only the lexer keeps it fast, and it can format code that's still being written.
  • Two entry points. formatLines streams (used by the CLI), and format(String) is a convenience built on it (TokenFormatter.kt:25–28). The TCK hands over a whole string, so it uses the convenience method.

Tests: 33 in FormatterTest10, FormatterTest11, FormatterEdgeCaseTest, FormatterStreamingTest and RulesReaderTest.

linter

depends on commons · jackson-module-kotlin 2.15

The linter is the static code analyzer. It reads a JSON config, builds the enabled rules for the version, and checks each statement as it streams by. Every violation is reported with its position.

Step by step

  1. Read the config. Linter.kt:19–22 passes the config to RuleJsonReader.kt:29–42, which uses Jackson and ignores unknown keys (:8). It normalises "camel case" and "camelcase" to the same value (:33) and returns rule names, not rule objects.
  2. Build rules for the version. RuleFactory.kt:6–21 maps names to rule instances. inputonly requires 1.1 (:19, :23–31), and asking for it under 1.0 is a configuration error.
  3. Stream and check. Linter.kt:38–48 runs every rule on one statement at a time, walking into blocks so a statement inside an if is checked like any other. Only the report grows, and it grows with the number of violations, not the file size.
  4. The rules.
    • CamelCaseRule.kt:10–22: an identifier must start lowercase and contain no _.
    • SnakeCaseRule.kt:10–21: only lowercase letters and _, with no __.
    • PrintOnlyRule.kt:9–18: a statement that starts with println must not contain an operator or a nested call. The predicates are in TokenPredicates.kt:9, 18.
    • The same class configured for readInput. The name is matched case-insensitively against the spelling the source used — nothing lowercases it first.
  5. Collect. LinterOutput.kt:13–24 stores typed BrokenRule(description, position) values. OutputFileManager can write .txt or .html reports, but neither the CLI nor the TCK uses it.

Decisions to defend

Rule interface + factoryRule.kt:6 · RuleFactory.kt:5
A new check is a new class plus one line in the factory. The config reader doesn't know rule classes exist, so a change in config format doesn't touch the rules.
Version gating in one placeRuleFactory.kt:23
readInput doesn't exist in 1.0, so its rule can't be enabled there, and the CLI reports that as a configuration error (exit code 2).
Rules over tokens, not over AST nodesLinter.kt:33
This keeps rules simple and uniform: identifier rules just filter IDENTIFIER tokens. The trade-off is that flattening loses block structure (see below).

Trade-offs to own

  • Flattened tokens lose structure. Rules see IDENTIFIER:c IDENTIFIER:a OPERATOR:/ …, not a tree. For the three rules in the spec that's enough, and each rule is about ten lines. A rule that needs nesting (say, "no println deeper than two blocks") would be the moment to add a tree-based rule interface next to this one.
  • The config reader returns names, not rules. That looks like an extra step, but it keeps Jackson out of the rule classes and puts the version check in one place (RuleFactory.kt:23).

Tests: 58 in LinterTests, RulesTests, LinterEndToEndTests, LinterStreamingTest and OutputFileManagerTest.

cli

application · depends on all six

The CLI turns printscript <operation> <file> [--version] [--config] [--output] into a command, runs it, and converts the outcome into an exit code. It is the only module that knows about files, the console and process exit.

Step by step

  1. Entry point. Main.kt:6–8: exitProcess(PrintScriptCli(ConsoleOutput()).run(args)).
  2. Parse arguments. ArgumentParser.kt:15–30 separates positional arguments from flags in a single pass (:39–55), then reads the operation (:70–76). It checks that the source file exists (:78–86) and that the version is supported, defaulting to 1.0 (:101–113). Config is required for formatting and analyzing (:88–99) via Operation.requiresConfig (Operation.kt:14–17).
  3. Build a command. CommandFactory.kt:36–46 constructs one of four Commands and all of its collaborators: the pipeline, a formatter from FormatterBuilder (:68), a linter with its version (:78–86).
  4. Run it. CliInvoker.kt:7 runs the command, and PrintScriptCli.kt:50–56 maps SUCCESS/FAILURE to exit codes.
  5. Handle errors once. PrintScriptCli.kt:26–48 is the only place that catches. PrintScriptException prints Error: describe() and exits 1. Usage errors print the usage line and exit 2. Invalid configuration exits 2, and I/O errors exit 1.
  6. Show progress while parsing. The assignment asks for this. ParsingPipeline.kt:30–46 wraps the node stream in onEach and reports each statement as it's parsed (:38–41). ConsoleProgressReporter.kt:14–22 rewrites a single stderr line using \r.
  7. The four operations. Validation consumes and counts nodes (ValidationCommand.kt:18–23). Execution runs the interpreter inside the stream (ExecutionCommand.kt:24–29). Formatting sends lines to a sink (FormattingCommand.kt:20–24). Analyzing returns FAILURE when there are violations (AnalyzingCommand.kt:21–33).
  8. I/O boundaries. Output has three channels: result goes to stdout, while info and error go to stderr (ConsoleOutput.kt:15–19). OutputPrinter.kt:14 adapts Printer to the result channel. ConsoleReader.kt:12–16 keeps one BufferedReader on stdin so no lines are lost between reads. FileSource.kt:17 closes the file after the block, and FileSink/OutputSink write formatted lines.

Streaming, versions and errors

requirements that touch every module

Sources that don't fit in memory

The first assignment says the lexer can't run to completion before parsing starts. The chain in Figure 1 is FileSource.useLines → Lexer.convertToTokens(Sequence) → StatementSplitter.split → Parser.map → interpreter.execute per node. What's held in memory is the current line plus the current statement.

The TCK enforces this with maxHeapSize = "7m" in its build.gradle. InterpreterLargeFileTest.java:22 feeds 128 × 1024 = 131,072 println statements. testWithCounter must finish with no errors. testWithCollector keeps every printed line and so must report "Java heap space" instead of crashing. That second test is why the adapter reserves 256 KB and frees it before reporting (InterpreterAdapter.java:36, 49, 64).

Positions are 0-based everywhere internally and become 1-based only when displayed: PrintScriptException.kt:29–31, AnalyzingCommand.kt:37–38, LinterAdapter.java:41. The lexer and parser report full ranges. The interpreter reports a start point only, because AST nodes store one position (InterpreterException.kt:9–11). A real example from the CLI:

Decisions under challenge

what we chose · what we didn't · the cost we accept

Graders rarely ask "what does this do?". They ask "why this and not that?". Each entry names the alternative a grader is likely to suggest, why ours fits this project better, and the cost of our choice. Naming the cost yourself shows you weighed the options; claiming there is none invites the follow-up question.

Lexer: one regex strategy per token kind

instead of a hand-written, character-by-character scanner

Why

Token kinds are data, not control flow. Version 1.1 is the 1.0 map plus six entries (TokenMapper.kt:61–70). A hand-written scanner would need version checks inside its loop.

Cost we accept

Pattern order matters (= before operators, number before identifiers), and invalid text needs the explicit gap check at Lexer.kt:85–103 because regex matching skips it silently.

Parser: a statement splitter plus a chain of factories

instead of one recursive-descent grammar, or a generator such as ANTLR

Why

The statement is the natural unit for streaming, and the splitter is the only piece that holds tokens (StatementSplitter.kt:8–11). Each construct lives in its own factory, so adding one touches a single class and a list. There's no generated code or extra build step to explain.

Cost we accept

Factories are chosen by which tokens appear, so the order of the list matters, and expressions are parsed by splitting on operators rather than by grammar rules. Both are manageable at PrintScript's size; a much larger language would push us toward a real grammar.

Streaming: a pull pipeline of Kotlin Sequences

instead of reading the whole file, or a producer/consumer with threads or coroutine Flows

Why

The consumer drives reading: asking for the next node reads just enough lines. It's single-threaded, needs no synchronisation or extra library, composes with map/onEach (ParsingPipeline.kt:38), and an exception surfaces at the statement that caused it.

Cost we accept

A sequence over a file is only valid while the file is open, which is why Source exposes useLines { } rather than a sequence (Source.kt:14). And statements before an error have already executed.

Interpreter: a registry of evaluators, one per node type

instead of a Visitor, or one large when over the sealed class

Why

A new node type is a new class plus a registration, and Interpreter never changes. Which constructs a version supports is visible in one list (InterpreterFactory.kt:14–47). A Visitor would force every visitor to change with each new node.

Cost we accept

Dispatch happens at run time, and each evaluator casts its node (BinaryEvaluator.kt:15), so a missing evaluator is a run-time error instead of a compile error. The linter's walks over the AST, where exhaustiveness matters more, use a when instead.

Runtime values are plain Kotlin Int, Double, String, Boolean

instead of a PrintScript value hierarchy (NumberValue, StringValue…)

Why

There are fewer classes, arithmetic and concatenation use Kotlin's own operators, and printing is toString(). The mapping back to PrintScript types is one small function (AssignmentEvaluator.kt:64–70).

Cost we accept

Evaluators use is checks, and Int/Double promotion needs explicit handling (ArithmeticOperations.kt:24–36). readInput's untyped text needed its own wrapper, ExternalInput.

Errors: exceptions that carry their position, caught at one boundary

instead of collecting a list of errors, or returning result types from every stage

Why

The spec and the TCK both report an error and stop. Stages stay free of error-passing code, the position travels with the exception, and each front end catches once: PrintScriptCli.kt:29 for the CLI and InterpreterAdapter.java:60 for the TCK.

Cost we accept

Only the first error is reported; a file with three syntax errors needs three runs. An IDE-style tool that lists every problem would need the parser to recover and collect errors.

Versions: assemble different components

instead of if (version == "1.1") inside logic, or separate modules per version

Why

Each module has exactly one place where the version is read (the table in Streaming, versions and errors), and the logic is shared. Rejecting 1.1 features under 1.0 is simply the component not being present.

Cost we accept

The version string is passed through several factories, and how clear the rejection is depends on the feature. const under 1.0 gets an explicit message ("Const declarations are not allowed in version 1.0"), while an if is reported as an invalid { character: accurate and positioned, but less descriptive.

Formatter: rewrite the gaps between tokens

instead of parsing to an AST and reprinting it

Why

A rule that isn't enabled must leave the source as written. The traced example keeps let b :number untouched while fixing the other lines (Example 2, traced). It also needs only the lexer and streams line by line.

Cost we accept

Every rule is expressed as a decision about one gap, with an explicit priority order (TokenFormatter.kt:59–76), and the formatter doesn't check syntax.

Linter: rules over each statement's flattened tokens

instead of visitors that walk the tree

Why

Every rule gets the same simple input, and each fits in about ten lines (CamelCaseRule.kt:10–14). Checking statement by statement keeps the linter streaming. Rules are built from config names by one factory, which also gates them by version.

Cost we accept

Block structure is flattened, so a future rule about nesting would need a tree-based rule interface next to this one.

Delivery: publish versioned Maven artifacts that the TCK consumes

instead of copying code into the TCK, or a Gradle composite build

Why

The TCK tests exactly what was released, the way any client would use it. CD publishes a snapshot from main and a release from each v* tag, running check first (cd.yml:34–50).

Cost we accept

After a change, you publish (publishToMavenLocal or CD) before the TCK sees it, and GitHub Packages needs credentials even for reading.

Likely questions

short answers with the line to show
How would you add PrintScript 1.2 with a while loop?

Add a WhileNode to the sealed AST; the compiler then flags the linter's walks (Statements.kt:74, Statements.kt:85) until it's handled. Add a version12Strategies() map with while (TokenMapper.kt:61), a WhileFactory in a 1.2 factory list (reusing ConditionalFactory's brace matching), and a WhileEvaluator in a 1.2 evaluator list. Finally add "1.2" to ArgumentParser.kt:113. No existing class changes its logic.

Why doesn't the parser depend on the lexer?

It only needs Token, which lives in commons. The CLI (ParsingPipeline.kt:48–51) and the TCK (Pipeline.java:25–28) connect the two. Either module can be replaced or tested without the other; parser tests use real tokens only through testImplementation.

Where are the SOLID principles?

SRP: StatementSplitter vs factories; ArgumentParser vs CommandFactory vs commands. OCP: the strategy, factory, evaluator and rule lists, where a version is just a list. LSP: the three PrintScriptException subclasses are caught as one (PrintScriptCli.kt:29). ISP: single-method Printer, Reader, Command. DIP: the interpreter depends on Printer/Reader, and commands on Source/Output, not on the console or files.

Which design patterns did you use?

Strategy (token classifiers, evaluators, lint rules), Factory (ParserFactory, InterpreterFactory, RuleFactory, CommandFactory, FormatterBuilder), Chain of Responsibility (Parser.kt:49), Command + Invoker (cli), Null Object (NilNode, NoOpProgressReporter), and Adapter (TCK, OutputPrinter).

How do you know it doesn't load the whole file?

The TCK runs 131,072 statements in a 7 MB heap (InterpreterLargeFileTest.java:22), and there are dedicated unit tests in each module: StreamingPipelineTest, FormatterStreamingTest, LinterStreamingTest and the CLI's StreamingTest. In the code, every stage signature takes and returns a Sequence.

How does readInput know what type to return?

It doesn't. It returns raw text wrapped in ExternalInput, and the destination converts it: the declaration, the assignment, or println as a string (ExternalInput.kt:16–27). An unparseable value fails there, positioned at the node.

Why is the formatter not built on the AST?

Because a rule that isn't enabled must leave the source untouched, and the AST has already discarded spacing. Working on token positions keeps everything (TokenFormatter.kt:6–15).

How is operator precedence handled?

By splitting at the lowest-precedence operator first (OperationFactory.kt:22–23), so it ends up at the root of the tree and is evaluated last. Parenthesised groups are skipped during the split and then parsed recursively (OperationFactory.kt:56–65).

Why Kotlin?

Sealed classes make the AST closed and checkable, Sequence gives lazy pipelines from the standard library, and data classes give tokens and nodes value equality for tests. It also runs on the JVM next to the Java TCK: our single-method Printer/Reader interfaces accept emitter::print directly (InterpreterAdapter.java:54).

How is it tested?

Three layers. First, 394 unit tests, with every module tested in isolation; the CLI uses in-memory Source/Output doubles (TestDoubles.kt). Second, dedicated streaming tests per stage. Third, the TCK as an external acceptance suite. ./gradlew check also enforces Ktlint, Detekt and an 80% coverage floor per module, on every commit (pre-commit hook) and every PR (CI).

What would you change with more time?

Answer with direction, not apology. Add a checking pass between parsing and execution, so type errors such as assigning a string to a number declared without a value are caught before anything runs. Give blocks their own variable scope. Make expression parsing split on the last operator of the lowest precedence, so chains like 10 - 2 - 3 group left to right. None of these are exercised by the TCK, and each fits inside the existing structure: the same factories, evaluators and lists.

What happens when the program has an error halfway through?

With lazy execution, the statements before the error have already run and printed, and then the error stops the run with its position. Validation mode reads the whole file without executing anything, so it's the way to check a file first.
