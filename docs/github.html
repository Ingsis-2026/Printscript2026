Say it like this

"Every change goes through a pull request to main. Continuous Integration runs ./gradlew check on each pull request and on each push to main: Ktlint, Detekt, every test and the 80% coverage check. Continuous Delivery publishes the seven modules to GitHub Packages. A merge to main publishes 1.0.0-SNAPSHOT, and pushing a tag like v1.0.0 publishes the release 1.0.0. The version comes from the tag, and CD runs the full check again before publishing. The TCK depends on com.github.ingsis-2026:*:1.0.0, so its CI tests exactly what we released."

The two workflows

Both live in .github/workflows and both call the same Gradle task as the pre-commit hook.

It runs on pushes to main and on pull requests targeting main (:3–7). There's one job: check out, install JDK 21 with the Gradle cache, run ./gradlew check. It has no special permissions and publishes nothing. It answers one question: is this commit healthy?

cd.yml · Continuous Delivery

  • Four triggers (:3–10): a push to main, a pushed tag matching v*, a published GitHub Release, and a manual run (workflow_dispatch).
  • Least privilege (:15–18): read the code, write packages. The built-in GITHUB_TOKEN is enough, so there are no personal secrets to manage.
  • The version is computed, not stored (:34–41). For a tag, ${GITHUB_REF_NAME#v} strips the v, so v1.0.0 becomes 1.0.0. Anything else gets 1.0.0-SNAPSHOT. PR #14 introduced the #v strip.
  • Check before publish (:43–44): the same quality gate runs again, so a tag on a broken commit can't publish.
  • Publish (:46–50): ./gradlew publish, with the Actions token and user passed as environment variables.

Release runbook

From a change on your machine to a new version the TCK can use. These are the commands the team's history shows; nothing here was run while preparing this sheet.

1

Start from an up-to-date main

As of 15 September your local main is behind GitHub: it still points at 7820da5, while origin/main and v1.0.0 are at d2661f8. Pull before a demo.

git switch main
git pull
git switch -c fix/short-description

Branch names in the history follow feat/…, fix/… and chore/….

2

Commit: the pre-commit hook runs the gate

scripts/pre-commit runs ./gradlew check and aborts the commit if it fails. It's copied into .git/hooks every time ./gradlew build runs (build.gradle.kts:5–17).

git add -A
git commit -m "fix: describe the change"

Commit prefixes in the history: feat:, fix:, refactor:, docs:, ci:, build:, chore:. If a style check fails, ./gradlew ktlintFormat fixes most issues.

3

Push and open a pull request: CI runs

Opening the PR triggers Continuous Integration on it. Every new push to the branch runs it again.

git push -u origin fix/short-description
gh pr create --base main --fill
gh pr checks --watch
4

Merge: CI and CD run on main, publishing the snapshot

The team merges with a merge commit ("Merge pull request #N"). The push to main starts both workflows, and CD republishes 1.0.0-SNAPSHOT.

gh pr merge --merge
gh run list --limit 3
5

Release: tag main and push the tag

This is the step that publishes a new version. Use the next semantic version: v1.0.1 for a fix, v1.1.0 for a feature. CD turns the tag into the version number.

git switch main
git pull
git tag v1.1.0
git push origin v1.1.0

This is how v1.0.0 was released: the tag points at the merge commit, and the push triggered the CD run that published 1.0.0.

6

Confirm the publish

Find the CD run for the tag and check which version it computed.

gh run list --workflow cd.yml --limit 3
gh run watch
gh run view RUN_ID --log | grep "VERSION:"

Replace RUN_ID with the number from gh run list. The published packages are listed on the repository's GitHub page under Packages.

7

Point the TCK at the new version

The TCK uses 1.0.0 by default. To test another version, pass it as a property; downloading from GitHub Packages needs credentials (see the TCK side).

./gradlew test -PprintscriptVersion=1.1.0

Pitfalls to avoid

  • Don't also create a GitHub Release for a tag you already pushed. release: published is a CD trigger too, so it would start a second publish of the same version. GitHub Packages doesn't accept re-uploading an existing non-snapshot version, so expect that second run to fail.
  • Tags need the v. CD only listens to v* (cd.yml:6–7). A tag named 1.1.0 publishes nothing.
  • If the tagged commit fails the check, nothing is published. Fix it on a new commit, delete the tag (git push origin :refs/tags/v1.1.0 and git tag -d v1.1.0), and tag again.
  • The snapshot label is fixed at 1.0.0-SNAPSHOT (cd.yml:40). After releasing 1.1.0, update it by hand to 1.1.0-SNAPSHOT.

Useful extras

Run CD manually, or rerun a run

The manual trigger publishes a snapshot from main. A rerun repeats a specific run, for example one that failed for a transient reason.

gh workflow run cd.yml --ref main
gh run rerun RUN_ID

Publish to your machine only

Installs the jars in ~/.m2, which the TCK checks first. Without VERSION the version is 1.0.0. On this machine ~/.m2 already holds 1.0.0 for all seven modules.

./gradlew publishToMavenLocal
VERSION=1.1.0 ./gradlew publishToMavenLocal

Quality gates, layered

The same ./gradlew check guards four points on the way to a published package.

  1. 1Pre-commit hook: blocks a commit that fails locally.scripts/pre-commit
  2. 2CI on the pull request: visible to reviewers before merging.ci.yml · pull_request
  3. 3CI on main: confirms the merged result, not just the branch.ci.yml · push
  4. 4CD before publishing: a broken commit, or a tag on one, never reaches GitHub Packages.cd.yml:43–44

check means Ktlint, Detekt, all tests, and JaCoCo verification at a minimum of 80% per module, wired in printscript.kotlin-common-conventions.gradle.kts:74–87.

Decisions to defend

Each with the cost we accepted.

Separate CI and CD workflows

CI answers "is this change healthy?" for every PR and needs no special permissions. CD answers "publish this" only for main, tags and releases, and is the only workflow with packages: write.

CostA merge to main runs check twice on the same commit, once in each workflow: about two extra minutes.

The version comes from the git tag

There's one source of truth, no "bump version" commits, and releasing is a single git push origin vX.Y.Z. The tag also records exactly which commit was released.

CostThe version isn't visible in the source, and local builds default to 1.0.0 unless VERSION is set.

A snapshot on every merge

Consumers like the TCK can test the latest main as 1.0.0-SNAPSHOT without waiting for a release, and releases stay deliberate.

CostThe snapshot label is hard-coded in cd.yml and has to be updated after each release.

Run the full check again before publishing

Publishing never trusts an earlier run: a tag can point at any commit, including one CI never saw.

CostAbout 1.5 minutes of each ~4-minute CD run.

GitHub Packages with the built-in token

The packages live next to the code, and CD publishes with GITHUB_TOKEN, so there are no personal access tokens stored as secrets.

CostConsumers need credentials even though the packages are public, which is why the TCK's build only adds that repository when credentials exist.

Pull requests as a team convention

All 14 changes went through PRs with CI checks, merged with merge commits so each PR stays visible in the history.

Costmain has no branch protection or rulesets (checked via the GitHub API), so nothing technically blocks a direct push. Requiring the CI check would enforce the convention.

Questions you might get

Short answers, with the file to show.

How do you publish a new version?

Merge to main, then git tag v1.1.0 and git push origin v1.1.0. CD strips the v, runs check and executes ./gradlew publish, which uploads all seven modules as 1.1.0.

What's the difference between 1.0.0-SNAPSHOT and 1.0.0?

The snapshot is republished on every merge to main, so it always means "latest main". 1.0.0 was published once, from the tagged commit d2661f8, and doesn't change. The TCK depends on 1.0.0.

What ran for PR #14, and what did it change?

CI on the PR (1m44s), then after the merge CI on main (1m54s) and CD publishing the snapshot (4m11s), then CD for the tag (4m6s). The change made CD strip the v from tag names, so tag v1.0.0 publishes version 1.0.0, the version the TCK asks for.

Why does CD run the tests again if CI already did?

A tag or a manual run can target a commit CI never checked, and publishing is the one step that can't be undone for a release version. Checking again in the same run that publishes makes that impossible to skip.

Where does the TCK get the PrintScript jars?

Locally from ~/.m2 (publishToMavenLocal). In the fork's CI from GitHub Packages, using the workflow token. Both resolve com.github.ingsis-2026:*:1.0.0.

Why are there yellow warnings on the Actions runs?

GitHub notes that actions/checkout@v4 and actions/setup-java@v4 target a deprecated Node.js version. The runs still succeed. Upgrading those actions to their next major versions removes the warnings.

Is main protected?

Not by settings: the API reports no branch protection and no rulesets. The team always used PRs with CI, and requiring the "Code Quality, Tests & Coverage" check would enforce it.
