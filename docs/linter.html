linter

The static code analyzer. It reads a JSON config, builds the enabled rules for the version, and checks each statement as it streams past, collecting every violation with its position instead of stopping at the first.

Say it like this

"The linter has two inputs. The JSON config is read into rule names, and a factory turns those into rule objects, rejecting any rule the chosen version doesn't support. The AST nodes come from the parser, one statement at a time. Each statement is flattened into a short list of tokens, and every rule checks that list. A rule is a small class: identifier rules filter identifiers by naming style, and the println and readInput rules look for an operator or a nested call among the arguments. Violations are collected, not thrown, so one run reports all of them with their positions, and only the report takes up memory."

The shape

Two lanes that meet at the validator.

From config to rules

Jackson reads the JSON, and the reader translates it into names.

Decisions to defend

Each with the cost we accepted.

Rules check flattened tokens per statement, not the tree

Every rule gets the same simple input, and each fits in about ten lines: identifier rules are a filter, and expression rules are a search for an operator or a call. Checking statement by statement keeps the linter streaming.

CostNesting is lost when a statement is flattened. A future rule about structure, such as nesting depth, would need a tree-based rule interface next to this one.

A Rule interface built by a factory

Strategy pattern: the validator applies any list of rules without knowing what they check, and a new rule doesn't change Linter or RuleValidator.

CostA new rule touches three places: its class, a branch in RuleFactory, and a property plus name in RuleJsonReader.

The config reader returns names, not rules

Jackson stays out of the rule classes, the JSON format can change without touching them, and the factory is the single place that decides which rules exist for a version.

CostAn extra step that looks redundant until you add a second config format or a new version.

A rule the version doesn't support is a configuration error

Enabling readInput checks for a 1.0 program is a mistake the user should see, so the CLI reports it and exits 2 instead of silently ignoring the rule.

CostA 1.1 config that includes inputonly can't be reused as-is for 1.0 sources.

Unknown keys are ignored

The TCK's configs, and future ones, can carry keys this version doesn't know (RuleJsonReader.kt:8), and the linter still runs the rules it does know.

CostA misspelt key is silently ignored rather than reported.

Collect violations instead of throwing

Unlike a syntax error, a style violation doesn't stop analysis. Users want every problem in one run, and the TCK expects one reported error per violation.

CostThe report grows with the number of violations. That's fine for real code; a file with hundreds of thousands of violations would hold them all.

Questions you might get

Short answers, with the line to show.

Why does the linter work on tokens and not directly on AST nodes?

The assignment's rules are about names and about operators inside a call. A flat token list answers both with a filter or a search, and the same input format serves every rule. The flattening already exists in commons (Tokenizer).

Why does analysis with violations exit 1 but not throw?

Finding violations means the tool worked. The command returns CommandStatus.FAILURE, and the CLI turns that into exit code 1 so scripts can react. Exceptions are for broken sources or configs.

What counts as "an expression" for the println and readInput rules?

Any OPERATOR token or nested FUNCTION token among the arguments (TokenPredicates.kt:18). Identifiers and literals are allowed, exactly the "identifier or literal" wording in the assignment.

How would you add a rule, say "no const declarations"?

Write NoConstRule : Rule, add a "noconst" branch in RuleFactory (gated to 1.1 like inputonly), and add a JSON property plus name in RuleJsonReader. Linter and RuleValidator don't change.

Why does the readInput violation point at the variable name?

Both expression rules report at the statement's first token (row[0]). For println that's println itself; for a declaration using readInput it's the declared name, which is where that line starts.

How does the version reach the linter?

As a LinterVersion enum built from the version string (LinterVersion.kt:11). The CLI and TCK convert it, and an unknown version is rejected before any linting.

What is OutputFileManager for?

It can render the violations as a .txt or .html report and save it to disk, and it's tested. It is not wired into the CLI or the TCK.
