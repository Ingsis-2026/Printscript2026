linter

The static code analyzer. It reads a JSON config, builds the enabled rules for the version, and checks each statement as it streams past, collecting every violation with its position instead of stopping at the first.

Say it like this

"The linter has two inputs. The JSON config is read into rule names, and a factory turns those into rule objects, rejecting any rule the chosen version doesn't support. The AST nodes come from the parser, one statement at a time. A rule is one function: give it a statement, it gives back the violations in it. There are two rules — one checks how identifiers are spelled, the other that a call's argument is a variable or a literal — and each is configured twice, which covers the four settings the config file offers. Violations are collected, not thrown, so one run reports all of them with their positions, and only the report takes up memory."

The shape

Two lanes that meet in check.

The version a rule appeared in is a property of the rule (RuleName.since, :12–18), so the factory has one check for all of them (:21) instead of a special case for inputonly. Asking for a minimum rather than an exact match is what lets a version after 1.1 keep the rule. Checked against the jar: under 1.0 it throws "Rule not available for this version"; under 1.1 it builds the rule. The CLI reports it as Error de configuración: Rule not available for this version and exits with code 2, a configuration problem rather than a problem with the source.

One interface with one method, two rules, and two short walks they share.

  • What counts as an expression (:30): the argument is a BinaryNode or another call. A variable or a literal isn't, which matches the assignment: println(x) and println(5) are allowed, println(1 + 2) isn't.
  • The name is matched case-insensitively (:22) against the spelling the language uses. Nothing lowercases it first any more.
  • Both settings report at the statement (:24), not at the call: println is a statement in its own right, so that is its position, while readInput always sits inside a declaration or an assignment, and the report points at where that statement starts.
  • The two settings differ by two arguments, supplied by the factory (:25–26).

Decisions to defend

Each with the cost we accepted.

Rules read the tree, one statement at a time

The parser already worked out the structure, so a rule asks the tree directly instead of a flattened copy of it: "is this call's argument an expression?" is one type test on one node. Checking statement by statement keeps the linter streaming, and blocks are handled by treating the statements inside them as statements, which is what makes a println inside an if get checked at all.

CostTwo short walks have to stay in step with the AST — one for the statements inside blocks, one for the nodes inside a statement. Both are exhaustive whens over the sealed class, so a new node type stops compiling until it is handled, but they are still two places rather than one.

A Rule interface built by a factory

Strategy pattern: check applies any list of rules without knowing what they check, and a new rule doesn't change Linter. The interface has one method, so a rule is a function from a statement to the violations in it.

CostA new rule touches four places: its class, a constant in RuleName, a branch in RuleFactory, and a property plus name in LinterConfig and RuleJsonReader. Three of the four stop compiling until they are done.

The config reader returns names, not rules

Jackson stays out of the rule classes, the JSON format can change without touching them, and the factory is the single place that decides which rules exist for a version.

CostAn extra step that looks redundant until you add a second config format or a new version.

A rule the version doesn't support is a configuration error

Enabling readInput checks for a 1.0 program is a mistake the user should see, so the CLI reports it and exits 2 instead of silently ignoring the rule.

CostA 1.1 config that includes inputonly can't be reused as-is for 1.0 sources.

Unknown keys are ignored

The TCK's configs, and future ones, can carry keys this version doesn't know (RuleJsonReader.kt:8), and the linter still runs the rules it does know.

CostA misspelt key is silently ignored rather than reported.

Collect violations instead of throwing

Unlike a syntax error, a style violation doesn't stop analysis. Users want every problem in one run, and the TCK expects one reported error per violation.

CostThe report grows with the number of violations. That's fine for real code; a file with hundreds of thousands of violations would hold them all.

Questions you might get

Short answers, with the line to show.

Why do the rules read the AST instead of a flat list of tokens?

Because the parser already worked the structure out. It used to flatten each statement back into tokens, and every rule then re-derived what the tree knew: "is this argument an expression?" became a scan for an operator among the neighbouring tokens, instead of one type test on one node. The round trip also cost accuracy — the flattening lowercased function names and threw away every token's end position — and it could not see into a block, so a println inside an if was never checked.

Why does analysis with violations exit 1 but not throw?

Finding violations means the tool worked. The command returns CommandStatus.FAILURE, and the CLI turns that into exit code 1 so scripts can react. Exceptions are for broken sources or configs.

What counts as "an expression" for the println and readInput rules?

The call's argument being a BinaryNode or another call (CallArgumentRule.kt:30). A variable or a literal is allowed, exactly the "identifier or literal" wording in the assignment.

How would you add a rule, say "no const declarations"?

Write NoConstRule : Rule with its one check method, add a NO_CONST constant to RuleName with the version it appears in — which stops RuleFactory compiling until you say how to build it — and add a property plus name in LinterConfig and RuleJsonReader. Linter doesn't change.

Why does the readInput violation point at the variable name?

The rule reports at the statement it is checking (CallArgumentRule.kt:24). println is a statement in its own right, so that is its own position; readInput always sits inside a declaration or an assignment, so the report points at where that statement starts — the declared name.

How does the version reach the linter?

As a LinterVersion enum built from the version string (LinterVersion.kt:11). The CLI and TCK convert it, and an unknown version is rejected before any linting.
