lexer

Turns source text into a lazy stream of tokens, one line at a time. Which words exist is decided only by the version chosen, and anything it can't recognise becomes an error with exact columns.

Say it like this

"Each version is an ordered list of token definitions: a type and the regex that recognises it. The lexer joins them into one regex, with one named group per definition, and scans the source one line at a time. Each match is a lexeme. Where the match starts and ends is the token's position, and the group that captured it is its type. When two definitions recognise the same text, the first one in the list wins, so a version's words come before identifiers. A word the version doesn't have simply isn't in its list, so it reads as an identifier. Whatever the pattern skipped over is checked too: anything that isn't whitespace is an invalid character, reported with its columns. Because the output is a Sequence, a line is read only when the parser asks for more tokens, so memory depends on the longest line, not on the file size."

Where it sits

Three callers in production code, each feeding it lines lazily. The list-returning execute is used only by tests.

All three build the lexer the same way, Lexer(TokenMapper(version)). The lexer never learns who consumes its tokens, and the parser never imports the lexer; the callers above connect the two. That's why the lexer depends only on commons.

Order is part of the design

At each position, Java's regex engine takes the first alternative that matches, not the longest one. So the order of the version's list decides what a lexeme becomes. This is 1.1's list, in order:

  1. 1\blet\bKEYWORD1.0
  2. 2\bprintln\bFUNCTION1.0
  3. 3\bstring\b|\bnumber\bDATA_TYPE1.0
  4. 4\bconst\bKEYWORDnew in 1.1
  5. 5\bif\b|\belse\bCONDITIONALnew in 1.1
  6. 6\breadInput\b|\breadEnv\bFUNCTIONnew in 1.1
  7. 7\bboolean\bDATA_TYPEnew in 1.1
  8. 8\btrue\b|\bfalse\bBOOLEANLITERALnew in 1.1
  9. 9\b[a-zA-Z_][a-zA-Z0-9_]*\bIDENTIFIER1.0
  10. 10'[^']*'|"[^"]*"STRINGLITERAL1.0
  11. 11[0-9]+(\.[0-9]+)?NUMBERLITERAL1.0
  12. 12[()]PARENTHESIS1.0
  13. 13:DECLARATOR1.0
  14. 14=ASSIGNATION1.0
  15. 15[-+*/%=><!&|^~]+OPERATOR1.0
  16. 16[\[\],;.]PUNCTUATOR1.0
  17. 17[{}]PUNCTUATORnew in 1.1
  • Words before IDENTIFIER (1–8 before 9). let is a KEYWORD because definition 1 is tried first. letter isn't cut short: \blet\b fails because no word boundary follows the t, so the identifier takes the whole word.
  • Every 1.1 word lands before IDENTIFIER too (4–8). Each version is assembled as words + names and literals + symbols (TokenMapper.kt:27–30), so 1.1 adds to the word list and can't end up behind the identifier by accident.
  • = before OPERATOR (14 before 15). x=-1 gives ASSIGNATION, then OPERATOR -. With the operator class first, it would swallow =- as one token. A side effect: ==, which isn't PrintScript, lexes as two ASSIGNATION tokens.
  • Names, literals and symbols never compete. They start with different characters (a letter or _, a quote, a digit, punctuation), so their order relative to one another doesn't matter.

The group that matched is the type

105    /**106     * Cada definición se busca por nombre y no por número de grupo, porque su regex puede tener107     * grupos propios (el de los decimales de NUMBERLITERAL) que correrían la numeración.108     */109    private fun groupOf(definitionIndex: Int): String = "definition$definitionIndex"

After a match, exactly one definition's group took part in it. typeCapturedBy finds it (:91): start(group) is -1 for every group that didn't. Groups are looked up by name (:109) because some definitions have groups of their own: NUMBERLITERAL's (\.[0-9]+) would shift every group number after it.

  • lines.mapIndexed(::tokenizeLine).flatten() (:31). Sequence operations are lazy, so a line is tokenized only when the consumer asks past the previous line's tokens. That's the first experiment: an infinite input can't hang it. mapIndexed supplies the row number.

Decisions to defend

Each with the cost we accepted.

The version decides the vocabulary; the lexer makes no rulings

There's no reserved-word table and no list of words "not allowed in this version". A version is its list of definitions (TokenMapper.kt:19–24), and a word it doesn't have isn't in the list. Before this change, one reserved table served both versions, so 1.0 lexed if and true as keywords of a language it doesn't have, and a second table existed only to reject const.

Costconst under 1.0 now gets the parser's generic Expected a KEYWORD token instead of a tailored message. It's accurate and still positioned at column 1.

An ordered list of definitions, not a hand-written scanner

Token types are data. A new token is a new entry, Lexer never changes (Open/Closed), and a version is a different list. A character-by-character scanner would need version checks inside its loop.

CostOrder matters. inOrder makes the recurring case structural (words before names), and the one exception, = before operators, is stated where it is written.

One pass: the group that matched is the type

The old lexer found each lexeme with the regex and then classified its text a second time. Once the order is right, that second pass could only repeat the regex's decision, or contradict it. Reading the type from the match (Lexer.kt:90–93) leaves one source of truth.

CostIt relies on group names (Lexer.kt:109), which are built and read in that one file. Finding the group checks at most 17 groups per token.

One pattern, compiled once per lexer

Pattern.compile is expensive, so it runs in the Lexer's initialiser (Lexer.kt:24–27), and each line only creates a cheap Matcher. A compiled Pattern is immutable and thread-safe; Matchers aren't, which is why one is created per line.

CostEvery token type has to be expressible as a regex. PrintScript's all are.

Lazy and line-granular

This meets the assignment's "sources that don't fit in memory" requirement. Memory is bounded by the longest line, rows come free from the line count, and the TCK's 131,072-line test passes in a 7 MB heap.

CostA token can't span lines, which is fine because PrintScript has no multi-line strings. An error later in a line surfaces before that line's earlier tokens are delivered.

Check the gaps instead of adding a catch-all group

The alternative is a last group (.) mapped to UNKNOWN. Checking the text between matches keeps the pattern made only of real token types, and it reports a whole invalid run, trimmed, with correct columns (Lexer.kt:71–77).

CostAbout 20 lines of explicit code, and the check must run in two places: before each token and at the end of the line.

Questions you might get

Short answers, with the line to show.

Why doesn't the lexer reject const in 1.0?

Because 1.0 doesn't have it. Which words exist is the version's decision, expressed as its list (TokenMapper.kt:32–37). The lexer only knows how to scan with whatever list it's given, so under 1.0 const is a name and the parser rejects the statement.

Why not a lexer generator like JFlex?

The vocabulary is 11–17 definitions, and 1.1 is 1.0 plus additions (TokenMapper.kt:39–47). A generator adds a grammar file, a build step and generated code to explain, and versioning would mean two grammars.

How does it know let is a keyword and letter isn't?

Order plus word boundaries. The words come before IDENTIFIER (TokenMapper.kt:30), so let is claimed by the KEYWORD group. Every word is wrapped in \b (TokenDefinition.kt:15), so \blet\b doesn't match inside letter, and the identifier takes the whole word.

Is if a valid variable name in 1.0?

For the lexer, yes: it's an IDENTIFIER. The parser still refuses let if: number = 1;, because its StatementSplitter recognises an if by its text, not its token type (StatementSplitter.kt:66). That's a gap in the parser, not the lexer.

Why does a string's value lose its quotes?

Everything downstream wants the content: the interpreter prints it, and the parser checks its type. The positions still cover the quotes, and the formatter re-reads the original text when it needs them (SourceToken.kt:51).

Is the lexer thread-safe?

A Lexer holds only its definitions and a compiled Pattern, both immutable. Each line creates its own Matcher (Lexer.kt:41), so one instance can serve several sources. Each returned sequence has its own state and should be consumed by one thread.

How would you add while for 1.2?

Add a word list that is 1.1's plus words(…, "while"), and a "1.2" branch in definitionsFor (TokenMapper.kt:19–24). inOrder puts it before IDENTIFIER. Lexer and TokenDefinition don't change.

What does execute(input) do?

It splits a whole string into lines and returns the tokens as a list (Lexer.kt:29). Tests use it for convenience; production code always uses the Sequence or InputStream overloads.
