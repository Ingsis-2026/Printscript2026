lexer

Turns source text into a lazy stream of tokens, one line at a time. Every lexeme it can't recognise, and every word the chosen version doesn't allow, becomes an error with exact columns.

Say it like this

"The lexer is built from a map with one regex per token type, chosen by version. It joins those regexes into a single pattern and scans the source one line at a time. The regex finds where each lexeme starts and ends. A second step decides its type, checking reserved words first. Whatever the pattern skipped over is checked too: anything that isn't whitespace is an invalid character, reported with its columns. Because the output is a Sequence, a line is read only when the parser asks for more tokens, so memory depends on the longest line, not on the file size."

Where it sits

Three callers in production code, each feeding it lines lazily. The list-returning overloads are used only by tests.

The lexer never learns who consumes its tokens, and the parser never imports the lexer; the callers above connect the two. That's why the lexer depends only on commons.

Order is part of the design

At each position, Java's regex engine takes the first alternative that matches, not the longest one. So the order of this list (which is the insertion order of the mapOf) decides what a lexeme becomes.

  2. 2println|readInput|readEnvFUNCTION+2 in 1.1

  • = before OPERATOR (5 before 7) makes x = 5 produce an ASSIGNATION token. It also means ==, which isn't PrintScript, lexes as two ASSIGNATION tokens rather than one operator.
  • KEYWORD and DATA_TYPE before IDENTIFIER (1 and 6 before 8), with \b word boundaries. let is a keyword, but letter doesn't start with a let token: \blet\b fails because no boundary follows the t, so the identifier pattern takes the whole word.
  • Groups 12 and 13 come after IDENTIFIER. In 1.1 they were added to the end of a copied map (TokenMapper.kt:63, 67), so the regex matches true and if with the identifier group. They still get the right type because of the second step below.

Two steps: find the lexeme, then decide its type

22    fun disallowedReason(input: String): String? = disallowedKeywords[input]2324    fun classify(input: String): TokenType {25        if (input.isBlank()) return TokenType.UNKNOWN2627        return reservedKeywords[input]28            ?: strategyMap.entries.firstOrNull { it.value.classify(input) }?.key29            ?: TokenType.UNKNOWN30    }

The regex only finds boundaries. classify then looks the text up in the reserved words (TokenMapper.kt:35–44) before trying strategies in order. That's what turns an identifier-shaped true into BOOLEANLITERAL and if into CONDITIONAL, whatever the alternation order. Reserved words are a fixed table, so their type never depends on where a pattern sits in the list.

29    fun convertToTokens(lines: Sequence<String>): Sequence<Token> =30        sequence {31            var row = 032            for (lineContent in lines) {33                val lineTokens = convertLineToTokens(lineContent, row)34                for (token in lineTokens) {35                    yield(token)36                }37                row++38            }39        }4041    fun convertToTokens(inputStream: InputStream): Sequence<Token> {42        val reader = BufferedReader(InputStreamReader(inputStream))43        return convertToTokens(reader.lineSequence())44    }
  • sequence { yield } (:30, :35) turns the loop into a generator: execution pauses at each yield until the consumer asks for the next token. That's the first experiment: an infinite input can't hang it.
  • The unit of work is a line. convertLineToTokens returns a complete List (:33), which is then yielded token by token. That's the second experiment: a bad character anywhere in a line fails before that line's tokens are delivered. Memory is bounded by the longest line.
  • The InputStream overload (:41–44) wraps a BufferedReader and reuses the same path. The caller owns the stream and closes it.

Decisions to defend

Each with the cost we accepted.

A strategy per token type, not a hand-written scanner

Token types are data in a map. A new token is a new entry, Lexer never changes (Open/Closed), and a version is simply a different map. A character-by-character scanner would need version checks inside its loop.

CostAlternation order matters, as the = vs OPERATOR and let vs IDENTIFIER examples show, so anyone adding a strategy has to think about where it goes.

Find the lexeme with the regex, decide its type with classify

Reserved words go through a fixed table first, so their type doesn't depend on alternation order. 1.1's true and if are matched by the identifier group and still come out correct.

CostEach lexeme is tested against the strategies a second time: at most 13 small matches calls per token. We chose readability over reading regex group indices.

One pattern, compiled once per lexer

Pattern.compile is expensive, so it runs in the Lexer's initialiser (Lexer.kt:14), and each line only creates a cheap Matcher. A compiled Pattern is immutable and thread-safe; Matchers aren't, which is why one is created per line.

CostOnly regex strategies take part in finding lexemes (PatternMatcher.kt:12). A non-regex strategy could classify text but would never be asked to find it.

Lazy and line-granular

This meets the assignment's "sources that don't fit in memory" requirement. Memory is bounded by the longest line, rows come free from the line count, and the TCK's 131,072-line test passes in a 7 MB heap.

CostA token can't span lines, which is fine because PrintScript has no multi-line strings. An error later in a line surfaces before that line's earlier tokens are delivered.

Reject version-specific words in the lexer, with a reason

The lexer is the stage that knows the lexeme's exact columns, so the const error points at const (TokenMapper.kt:15–21). Doing it inside classify would have thrown without a position.

CostOnly const gets a tailored message. Other 1.1 features fail as an invalid { or in the parser, which is accurate and positioned but less descriptive.

Check the gaps instead of adding a catch-all group

The alternative is a last group (.) mapped to UNKNOWN. Checking the text between matches keeps the pattern made only of real token types, and it reports a whole invalid run, trimmed, with correct columns (Lexer.kt:95–101).

CostAbout 20 lines of explicit code, and the check must run in two places: before each token and at the end of the line.

Questions you might get

Short answers, with the line to show.

Why not a lexer generator like JFlex?

The vocabulary is 11–13 patterns, and versions are map differences (TokenMapper.kt:61–70). A generator adds a grammar file, a build step and generated code to explain, and versioning would mean two grammars.

How does it know let is a keyword and letter isn't?

Two layers. In the regex, KEYWORD comes before IDENTIFIER and uses \b, so letter doesn't match \blet\b. In classify, the reserved-word table is checked first (TokenMapper.kt:27), and letter isn't in it.

Why does a string's value lose its quotes?

Everything downstream wants the content: the interpreter prints it, and the parser checks its type. The positions still cover the quotes, and the formatter re-reads the original text when it needs them (SourceToken.kt:51).

Is the lexer thread-safe?

A Lexer holds only its mapper and a compiled Pattern, both effectively immutable. Each line creates its own Matcher (Lexer.kt:51), so one instance can serve several sources. Each returned sequence has its own state and should be consumed by one thread.

Why is if a CONDITIONAL token even in 1.0?

The reserved-word table is shared by both versions (TokenMapper.kt:7). That's harmless: a 1.0 if program can't get past the {, and the 1.0 parser has no ConditionalFactory anyway.

How would you add while for 1.2?

Add a version12Strategies() that copies 1.1 and adds \bwhile\b, put "while" in the reserved table so pattern order can't affect it, and add a "1.2" branch to both version switches (TokenMapper.kt:74–86). Lexer and PatternMatcher don't change.

What does execute(input) do?

It's an alias for convertToTokens(String), which returns a list (Lexer.kt:16). Tests use it for convenience; production code always uses the Sequence or InputStream overloads.
