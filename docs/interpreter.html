interpreter

Executes AST nodes one at a time against three small tables of state. Output and input go through two one-method interfaces, so the same code runs in the CLI and inside the TCK.

Say it like this

"The interpreter holds a list of evaluators, one per node type, and the version decides which are in the list. execute(node) finds the evaluator that can handle the node and runs it. Evaluators never call each other: to evaluate a child they go back through interpreter.execute. That single entry point is also where errors get their position, from the innermost node that failed. State is three maps: values, the let/const keyword, and each declared type. println and readInput go through injected Printer and Reader interfaces, which is how the TCK supplies its own input and collects the output."

The interpreter imports neither the lexer nor the parser. It receives ASTNodes from commons and never learns where they came from.

The core loop

One class holds the state, and a list of evaluators holds the behaviour.

Decisions to defend

Each with the cost we accepted.

An evaluator per node type, in a list, instead of a Visitor or one big when

A new node type is a new class plus a list entry, and Interpreter doesn't change (Open/Closed). The version is the list (InterpreterFactory.kt:28–56). A Visitor would require changing every visitor whenever a node type is added.

CostDispatch is a run-time search, and each evaluator casts its node (node as BinaryNode), so a missing evaluator is a run-time error rather than a compile error.

All recursion goes back through interpreter.execute

There's one entry point for dispatch and one place that positions errors (Interpreter.kt:36–41). Evaluators stay independent of each other, and none of them handles positions.

CostEvery child evaluation repeats the search (at most 9 canEvaluate calls), and errors carry a start position but no end.

Printer and Reader are injected

Dependency inversion. The spec asks for "a mechanism to provide values" when the interpreter is used programmatically. The CLI plugs in stdout/stdin, the TCK plugs in its emitter and provider as method references, and tests capture output in a list.

CostreadEnv still reads System.getenv directly (FunctionEvaluator.kt:56), so tests depend on the real environment. The TCK's build.gradle sets a variable for exactly that reason.

Plain Kotlin values, with Int kept separate from Double

There are fewer classes, Kotlin's operators and toString() do the work, and whole numbers print without .0, which the spec's examples require (Result: 3).

Costis checks across evaluators and an explicit promotion table (ArithmeticOperations.kt).

External input stays untyped until its destination is known

It follows the spec literally: the type comes from the variable, or is string inside println. The same "41" correctly becomes a number or a string.

CostEvery place that receives a value has to resolve it: declaration, assignment and print. A fourth destination would need the same call.

State as three maps on the interpreter

Evaluators hold no state, so a single instance of each can be shared, and state is easy to inspect in tests: the tables above were printed straight from the maps.

CostAny evaluator can write to any map. Moving the maps into an Environment class would be the natural next step, and also the place to add block scopes.

Questions you might get

Short answers, with the line to show.

Why not a Visitor pattern?

A Visitor needs a method per node type on every visitor, so adding a node changes them all. With evaluators, adding a node adds a class, and versions are just lists. The cost is losing compile-time exhaustiveness; the Tokenizer in commons, where exhaustiveness matters more, uses a when instead.

Why does a division by zero point at the / and not at the declaration?

The error is thrown inside BinaryEvaluator. The innermost execute, the one for the BinaryNode, catches it first and adds that node's position, the operator. The outer call for the declaration sees a position already set and rethrows it unchanged (Interpreter.kt:39).

Why keep Int and Double apart if PrintScript has one number?

So whole numbers print as whole numbers. Example 2 must print Result: 3, and a Double would print 3.0. For type checks they're the same PrintScript type (AssignmentEvaluator.kt:64–70).

How does readInput know its type?

It doesn't. It returns ExternalInput, and the declaration, assignment or println that receives it converts it with asType. A value that can't be converted fails there, like "41" for a boolean.

How is const enforced?

The declaration records the keyword (DeclarationEvaluator.kt:33), and any later assignment to that name checks it and throws (AssignmentEvaluator.kt:50–53).

What happens if the program fails halfway?

Statements before the failure have already run, as the one, two measurement shows. That's inherent to executing while streaming. The CLI's validation operation parses the whole file without executing anything.

How does the TCK provide input?

Its InputProvider has the same shape as our Reader (one method, string in, string out), so the adapter passes provider::input directly (InterpreterAdapter.java:54).
